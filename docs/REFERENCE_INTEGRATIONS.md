# Reference integrations — Davis & AdaptQuiz

Ten suites across two unrelated domains: an AI SDR and an adaptive-learning system. They exist
to demonstrate that a real domain can be expressed entirely in suites, policies, fixtures, and
calibration sets — **without the platform knowing anything about it**.

That claim is enforced, not asserted. `scripts/check-domain-leak.sh` fails the build if the
strings `davis` or `adaptquiz` appear anywhere under `apps/` or `packages/`. It caught the
reference-suite *test file* on its first run, which is why that file lives in the top-level
`tests/` tree: a platform test enumerating example domains is platform code that knows about
them.

```bash
# Any of the ten. No provider key, no network, no server.
uv run proofstep eval evals/suites/davis-lead-ranking.yaml
uv run proofstep eval evals/suites/quiz-security.yaml --model-client examples.stub_judge:make_client
```

## The suites

| Suite | Mechanisms | Judges | What it demonstrates |
|---|---|---|---|
| `davis-lead-ranking` | IR stats + deterministic | **0** | ranking is measurable against labels; a judge would be worse |
| `davis-research` | deterministic + 1 judge | 1 | where the deterministic/judge line falls |
| `davis-email` | 5 deterministic + 1 judge | 1 | placeholder leakage is a regex, not a judge |
| `davis-reply-intent` | classification + calibration | 0 | protected metrics, and defence in depth |
| `davis-agent-policy` | trajectory only | **0** | safety properties invisible to output evaluation |
| `davis-meetings` | deterministic + stats + 1 judge | 1 | dates and owners are exact; only prose needs a judge |
| `quiz-ingestion` | **all deterministic** | **0** | where evals are the wrong tool entirely |
| `quiz-questions` | 6 deterministic + 1 judge | 1 | a judge cannot arbitrate factual correctness |
| `quiz-learning` | AUC + calibration + 1 judge | 1 | ordinary supervised evaluation, not an eval |
| `quiz-security` | trajectory + deterministic | 0 | cross-tenant leakage is only visible in the trace |

Six of ten have **zero or one** judge. Roughly 60 % of the metrics across all ten are
deterministic or statistical, which is what a well-designed suite looks like: cheap checks
everywhere, judges reserved for the genuinely subjective residue. A suite that is mostly judges
has usually mis-modelled the problem, and `proofstep validate` says so.

## The measurements that make the arguments

These are the actual numbers from a clean run and the injected regression, not illustrations.

**Aggregates hide what matters.** Break the lead scorer so it promotes disqualified leads:

```
top10_ndcg_at_10      0.935 → 0.868   ✓ still passes its 0.75 gate
no_top_disqualified   1.000 → 0.267   ✗ blocking
```

The quality metric barely moves. The deterministic floor catches it.

**Trajectory sees what output cannot.** Break tenant isolation in the RAG agent:

```
tenant_isolation      1.0 → 0.0   ✗ caught 100% of the leaks
only_own_documents    1.0 → 0.5   ✗ caught 50%
citation_ownership    1.0 → 0.5   ✗ caught 50%
```

The output checks catch half, because half the fixtures have no other-user documents to cite —
the leak happened and left no trace in the artifact. The trajectory rule catches all of it.

**Ordinary ML evaluation beats a judge.** Break the mastery model so it ignores history:

```
mastery_auc           0.700 → 0.500   ✗ exactly chance
```

No judge involved, and no judge could have said it more clearly.

## Thirteen regressions, thirteen gates

Every suite ships an environment flag that injects a real defect, and a test asserts the run
**fails** through the specific gate meant to catch it. A suite whose gates cannot fire gives
false assurance, which is worse than no suite — so the load-bearing test in
`tests/test_reference_suites.py` is the one that expects exit code 1.

| Flag | Gate that fires |
|---|---|
| `DAVIS_BREAK_RANKING` | `no_top_disqualified` |
| `DAVIS_BREAK_CITATIONS` | `citation_present` |
| `DAVIS_BREAK_GROUNDING` | `claim_groundedness` (judge) |
| `DAVIS_BREAK_PLACEHOLDERS` | `no_placeholders` |

## Fixtures and their construction

Generated by `scripts/gen_reference_fixtures.py`, with the **output committed**. A fixture that
regenerates on every run is a fixture whose numbers move under you, and CI asserts the generators
reproduce byte-identically.

Three construction rules, each learned by getting it wrong first:

**Labels must correlate with the signals.** The first lead-ranking fixture assigned human quality
labels at random, so the scorer had nothing to find: P@5 came out at 0.45 and the gate thresholds
would have been arbitrary numbers. Labels are now derived from the observable signals plus noise,
which is what makes the task learnable and the gates meaningful.

**Hazards go in the input; defects come from a flag.** The first agent-policy fixture encoded
scenarios the agent deliberately failed, which made a compliance floor of 1.0 unpassable and
turned the suite into an assertion that the policy still had thirteen rules. Now the fixture
supplies adversarial *situations* — suppressed recipient, unsubscribed prospect, calendar conflict
— a correct agent handles all of them, and the flag is what breaks it.

**A calibration set must present the judge with the view it gets at run time.** The first sets put
a plain string where the judge's `inputs` named `output.claims_with_sources`, so every call
resolved nothing and errored. That reads as "0 usable labelled examples" rather than as a shape
mismatch, which cost an hour.

## Calibration

Five judges, each with a 120-example labelled set carrying a doubly-labelled subset and three
deliberate annotator disagreements, so the human ceiling has something real to report.

```
claim_groundedness        κ 0.950  agreement 0.975  false pass 0.017  ceiling 0.750
citation_support          κ 0.983  agreement 0.992  false pass 0.017  ceiling 0.750
grounded_personalization  κ 0.800  agreement 0.400  false pass 0.014  ceiling 0.958
summary_factuality        κ 0.789  agreement 0.392  false pass 0.014  ceiling 0.958
next_question_relevance   κ 0.789  agreement 0.392  false pass 0.000  ceiling 0.958
```

**The rubric judges' agreement of ~0.39 is not a problem, and it is worth understanding.** Exact
agreement on a 1–5 scale penalises a 4-vs-5 disagreement exactly as harshly as 1-vs-5, so it is
the wrong statistic to threshold. Weighted κ is distance-aware and is where the real bar sits;
the agreement floor is kept low deliberately, so it catches a judge that has stopped answering
rather than one that is a point off. Setting `min_agreement: 0.80` on an ordinal scale was the
first attempt and would have failed three healthy judges.

`min_per_class` is lowered to 20 for the ordinal sets. The default of 50 would demand 250
annotations across five rubric points to sharpen a statistic that is not per-class; the floor
still guards against a rubric point being entirely unmeasured, which is what it is for.

**In a real project these labels come from people.** The sets here are fixtures whose correct
label is determined by construction, and the generator says so. A set labelled by a model makes
calibration circular.

## The stub judge

`examples/stub_judge.py` is a deterministic `ModelClient` that answers from the fixture's markers.
It exercises the entire judge machinery — structured output, the canary check, the input
allow-list, cost and latency accounting, self-consistency voting, the calibration path — for free,
on a fork pull request where there are no secrets by design.

It is **not** a judge and must never be read as one. It has a fixed 1 % error rate so calibration
reports look like real ones rather than reporting κ = 1.0, and that rate was chosen so the suites'
*principled* thresholds pass with headroom — rather than loosening a considered false-pass limit
to accommodate a fixture, which is precisely the anti-pattern this project argues against.

One trap it exposed: the stub originally read the whole prompt, and a well-written rubric quotes
its boundary cases — so the groundedness rubric's mention of the Lisbon example made every claim
come back unsupported. It now reads only the content block.

## Gaps this phase closed in the platform

Building the suites surfaced three real holes:

- **`proofstep eval` had no way to supply a model client**, so judges were unreachable from the
  CLI. Now `--model-client module:factory` (or `PROOFSTEP_MODEL_CLIENT`), refused up front when a
  suite has judges and none is given.
- **A classify-mode judge could not be gated on.** It emitted a label and no numeric value, so a
  gate on it reported "metric missing" *after* the judge calls were paid for. `passing_labels`
  turns the label into a rate. This was latent in the Phase 7 reply-tone suite, which had exactly
  that gate and had only ever been calibrated, never run.
- **No AUC evaluator**, so the one metric the docs single out as "where teams wrongly reach for a
  judge" was inexpressible. `discrimination` computes ROC-AUC by the rank-sum identity, which
  handles ties correctly — and ties are constant when a predictor emits a handful of discrete
  probabilities.

## Not built

- **Wiring to real applications.** These are self-contained simulations. Pointing them at a live
  SDR or quiz service needs those services and their credentials; the suite YAML would change by
  one `entrypoint` line each.
- **`custom_python` and `business_rule` evaluators.** Two metrics that want them
  (`citation_location`, `claims_approved`) are computed in the task instead, which works but puts
  evaluation logic in the application.
- **Embedding-based deduplication.** The token-set check catches a re-emitted question but not a
  genuine paraphrase. Loosening its threshold to reach paraphrases would start flagging distinct
  questions on the same topic, which is worse than the gap.
- **A real grammar checker.** The stand-in checks that a stem is a well-formed question.
